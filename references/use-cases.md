# 文档以外的场景

STE 是为飞机维修手册造的。它的性质——一个词一个意思、短句、条件在前——适用于任何「读错有代价」的文字。

到 Issue 8 结束时，注册的 STE 用户里 64% 在航空和国防以外。

每个场景给出模式和的改写办法。

## 报错信息和命令行输出

模式：程序性。这是价值最高的目标：报错信息是凌晨两点给一个紧张的人看的指令。

写法：先说发生了什么（一般过去时），已知原因再说原因，最后给修法和条件。

> **改前：** 哎呀！在尝试建立连接时出了点问题。请确保你的凭证已正确配置，然后重试。
> **改后：** 数据库连接失败。用户 `app` 的密码不正确。设置 `DB_PASSWORD`，然后重新连接。

## 运维手册和标准作业流程

模式：偏严格的程序性。这是 STE 的主场——on-call 手册就是维修手册。

- 每一步都是祈使句，一步一条指令，条件在前。
- 警告放在这一步之前，命令在前，风险在后。
- 20 词上限硬执行：值班压力下的操作员每句只读一遍。

## 事故报告和复盘

模式：描述性。只用一般过去时——用完成时写的「我们已经发现……」会藏住事情发生的时间点。

> **改前：** 我们已经发现了一个问题，它可能影响了部分用户访问服务的能力。
> **改后：** 14:02 到 14:31 UTC 之间，12% 的请求失败。14:00 的一次部署移除了缓存预热步骤。

STE 禁止含糊词（「可能影响」）。报告只说已知的事，其余写「未知」。这样读起来更可信，因为事实如此。

## 提交信息和 PR 描述

模式：正文描述性，标题祈使式。现有习惯已经和 STE 一致：标题祈使句，正文平铺直叙过去的事实。
正文套替换表，用 25 词上限。删掉「本次 PR 旨在」。

## API 变更日志和发布说明

模式：描述性。一条记录一个变更，能一句就一句。
「破坏性变更」按警告模式写——命令在前：「把调用改到 `v2/users`。`name` 字段拆成了 `first_name` 和 `last_name`。」

## 写给 AI agent 的指令（提示词、AGENTS.md、skill）

模式：程序性。系统提示词是一个由无法提问的读者执行的程序——正是 STE 设计时针对的读者。

- 一句一条指令，保证每条规则可以独立引用，不容易只做一半。
- 一个词一个意思，避免模型把「检查」「核实」「校验」当成三种不同操作。
- 条件在前（「如果构建失败，停止」）比条件后置好，后置条件模型会丢掉。
- 不用 should——模型把它读成可选。写 must，或者删掉这条规则。

## 客服话术和状态页更新

模式：描述性，25 词上限。很多产品的用户大多数是非母语读者。
不要写「对于由此给您带来的任何不便，我们深表歉意」。
写：「API 中断了 18 分钟。这段时间内的上传已保存，今天会处理。」

## 翻译和本地化准备

模式：严格。STE 的初衷就是让非母语维修人员读懂英文，同时它也是机器翻译的预编辑。
一个词一个意思加完整语法（量词、连接词）能消掉大部分翻译歧义。文档要本地化时，STE 能降错误率和成本。

## UI 文案和空状态

模式：程序性，长度硬限制。按钮和标签是技术名称（豁免）。正文按规则走：
「还没有项目。创建一个项目即可开始。」这个长度下也活不下别的东西。

## STE 不适用的地方

营销页、发布帖、博客语气、品牌文字。STE 按设计删掉劝说性。
这些用你自己的语气写，然后对落地页链接的文档用 STE。
